# Hyde Dialog Widget

Use this skill when the target UI surface is a `HydeDialogWidget`: creating a new
dialog-style plugin from a spec, or normalizing an existing one.

Always read `.agents/protocols/hyde/widget-family.md` first. It carries the shared
workflow, the `widget_ir` / `python_source()` contract, ownership split, override
discipline, and test expectations. This file covers only the footer and preview
contract.

If the feature spec does not exist or is stale, use `add-hyde-ui-feature` first.

For the dialog checklist, read [references/dialog-pattern.md](references/dialog-pattern.md).
For a starting skeleton, copy `assets/template_plugin/` and rename the placeholders.

## Footer And Preview Contract

`HydeDialogWidget` owns the common footer behavior:

- one backing preview string set through `set_preview_string(...)`
- base `can_do_it()` follows whether that backing string is non-empty
- `Do It`, `To Cmd Line`, and `To Clip` all use that backing string
- `Help` is file-backed through `help_filename`

The backing string is **generated by the dialog's `widget_ir`**, never assembled in
the dialog. The canonical refresh path is:

```python
self.widget_ir = self.build_widget_ir(selection)
payload = "" if self.widget_ir is None else self.widget_ir.python_source(log=False)
self.set_preview_string(payload)
self.refresh_shell()
```

`HydeFileDialog` already implements exactly this in
`refresh_from_file_selection()`; subclasses supply `build_preview_state(...)` and
inherit the rest. Extend that path through hook overrides and `super()` rather than
building an alternate generation or submission path.

The lower pane may show different text only when the product genuinely needs it:

```python
self.set_preview_string(payload, display_text=status_or_help_text)
```

Backing string is what executes and copies. Display text is an exception, not the
default. A dialog that shows validation status still owes a backing command
contract whenever the selection is valid.

## Workflow

1. Confirm the surface really is a `HydeDialogWidget`, not a tool or interactive
   widget.
2. Inventory overrides of `handle_do_it()`, `can_do_it()`,
   `can_send_to_cmd_line()`, `do_it_dispatch_mode()`, and `handle_help()`.
3. Delete the ones that only return stored preview text or forward to shared
   dispatch; move any state updates into the dialog's real refresh path.
4. Route the preview through `widget_ir.python_source()`.
5. Keep only overrides with real policy: local validation beyond payload presence,
   visible-vs-hidden dispatch, or a genuine display-vs-payload difference.
6. Reuse any documented family-level seam — for figure-working dialogs, the
   `HydeFigureDialogWidget` base and the `EditableFigureContext` adapter — rather
   than inventing dialog-local policy.
7. Prove the contract with tests on what the user sees and what gets executed or
   copied.

## Normalization Targets

- no subclass `To Cmd Line` / `To Clip` when base behavior is enough
- no launcher-side post-accept dispatch duplicating dialog `Do It`
- no dialog-local help when `help_filename` is enough
- no duplicated preview string beside the base backing string
- no separate payload getter when `preview_string()` is the real contract
- no locally assembled command text where `widget_ir.python_source()` belongs
- no dialog-local policy duplicating a documented family-level rule

## Planning Handoff

When paired with issue work, make the plan state:

- whether the dialog is standard preview-backed or a real display-text exception
- what its `widget_ir` is, and which package IRs it composes
- whether `Do It`, `To Cmd Line`, and `To Clip` share one backing string
- whether `Help` is base-owned through `help_filename`
- whether any family-specific ownership or lifecycle rule must be reused
- whether the launcher only opens the dialog or still has a second dispatch path
- which tests prove the shared footer contract
