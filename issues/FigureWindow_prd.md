## Problem Statement

The user needs a way to visualize data within Hyde using matplotlib, but maintaining Hyde's strict architectural separation between the GUI (PyQt) and the execution kernel (`spyder_kernels`). Existing matplotlib backends do not adhere to Hyde's "Central Dogma", where the GUI must be a purely reactive, dumb viewport and all state must reside in the kernel. Additionally, users need Igor Pro-like workflows for figures, specifically the ability to save figure recreation macros upon closing a figure and easily accessing these saved macros from the main window menu.  Like the existing Table features, figures should update to show the current status of the plotted data, not be static like usual matplotlib figures.

## Solution

Implement a dedicated, custom matplotlib backend that delegates rendering and interactivity to the PyQt GUI via `comm` channels, while keeping all matplotlib state in the IPython kernel. 
Introduce a native MDI child window in Hyde to serve as the figure viewport.
Add UI and kernel logic to prompt users to save a "recreation macro" when closing a figure.
Extend the Hyde window menu to display saved figure macros and execute them by name.
Implement this as a plugin, and make few-to-no changes to the main GUI code base.

## User Stories

1. As a user, I want to plot data using standard matplotlib commands in the kernel so that I don't have to learn a new plotting API.
2. As a user, I want Hyde to prefer matplotlib's explicit object-oriented interface (for example `fig = plt.figure()`, `ax = fig.add_subplot(...)`, `ax.plot(...)`) over the implicit pyplot / MATLAB-style state-machine interface, so that generated and saved plotting code is explicit and reproducible.
3. As a user, I want Hyde to prefer subplot construction patterns based on `GridSpec` or equivalent explicit layout objects, so that even multi-panel figures remain explicit and reproducible rather than relying on compact implicit subplot codes.
4. As a user, I want my active matplotlib figures to appear as native MDI child windows within Hyde, so that they integrate seamlessly with the rest of the Hyde interface.
5. As an architect, I want the figure window to act as a dumb viewport driven by a custom matplotlib backend over `comm` channels, so that no analytical state is held in the PyQt process.
6. As a developer, I want the custom matplotlib backend to be built from scratch rather than monkey-patched, so that I have a clean foundation for future interactive features like user-placeable cursors.  Subclassing an existing backend, or using one as a starting template is expected.
7. As a user, I want to be prompted to save a figure recreation macro when I close a figure window, so that I can easily reproduce the plot later.
8. As a user, I want the option to discard the figure without saving a macro, so that I don't clutter my workspace with temporary exploratory plots.
9. As a user, I want to name my saved figure recreation macros, so that I can identify them easily.
10. As a user, I want my saved figure macros to appear in a persistent menu registry (e.g., Windows -> Graph Macros), so that I can access them at any time.
11. As a user, I want to reopen a saved figure by clicking its name in the menu, which should dispatch the macro string to the kernel, so that I can perfectly recreate the figure state.  Items 9-11 follow the same pattern as for tables so code should be reused.

## Implementation Decisions

- **Implementation pattern:** Implementation will follow the same overall pattern in the existing Table plugin.
- **Figure command strings:** Figures will be generated by sending standard matplotlib commands to the kernel. These commands should operate outside of Hyde if desired, provided the variables exist in scope.
- **Preferred plotting interface:** Hyde should prefer matplotlib's explicit object-oriented interface over the implicit pyplot / MATLAB-style state-machine interface. Generated examples, saved recreation macros, and GUI-emitted figure-edit commands should favor patterns such as `fig = plt.figure()`, `ax = fig.add_subplot(...)`, and `ax.plot(...)` rather than implicit calls like `plt.plot(...)` acting on hidden global state.
- **Preferred subplot construction:** Hyde should prefer explicit subplot layout construction based on `Figure.add_gridspec(...)` and related `GridSpec` variants rather than compact implicit subplot codes as the long-term figure layout idiom.
- **Initial GUI editing scope:** The initial GUI editing surface should support only a single subplot layout equivalent to `111`. Multi-panel `GridSpec` construction should remain valid in kernel-authored code and saved scripts, but GUI-side editing of subplot structure is initially limited to the single-subplot case.
- **`hyde_backend.py` (Kernel Module):** A new module defining a custom matplotlib backend. It will likely inherit from core matplotlib backend classes (e.g., `FigureManagerBase`, `FigureCanvasBase`) and existing backends and communicate with the GUI via IPython `comm` channels. It will send rendering instructions/data to the GUI.
- **`FigureWindow` (GUI Component):** A new PyQt MDI sub-window class that acts as the viewport for the matplotlib backend. It receives drawing commands over the `comm` channel and renders them natively.
- **Close Event Handling:** The `FigureWindow.closeEvent` will be intercepted to display a "Save window recreation macro as:" prompt. The UI interaction will generate a string command sent to the kernel to save the script state.
- **Macro Registry & State:** The kernel will maintain a registry of saved figure macros in the project state. When a macro is saved or deleted, the kernel will broadcast a metadata notification to the GUI.
- **Figure save scripts:** The save scripts will be standard matplotlib / numpy and there will be no custom Hyde dialect. Saved figure recreation code should also follow the explicit object-oriented matplotlib style rather than the implicit pyplot state machine.
- **Recreated figure layout style:** When a saved or GUI-generated figure uses only one subplot, the recreation code may use a single-subplot form equivalent to `fig.add_subplot(111)`. When Hyde later supports richer GUI-authored layouts, recreated code should prefer `GridSpec`-style construction.
- **Menu Generation:** The GUI will react to the macro registry metadata notifications by dynamically updating the "Windows -> Graph Macros" menu.
- **Macro Execution:** Clicking a menu item will construct a human-readable Python string and dispatch it to the kernel, satisfying the "GUI is a String Factory" rule.
- **Adherence to Central Dogma:** No array data or figure state will live in the GUI. The custom backend ensures all state remains in the kernel.

## Testing Decisions

- **What makes a good test:** Tests should verify the external behavior of the communication layer and the state management, without tightly coupling to the specific UI pixel rendering.
- **Modules to test:** 
  - The custom matplotlib backend's ability to serialize and send figure updates over `comm`.
  - The kernel's macro registry manager (saving, listing, and retrieving macros).
  - The GUI's ability to parse incoming figure `comm` messages and instantiate the `FigureWindow`.
  - The GUI menu generation logic based on state updates.
- **Prior art:** Existing tests for `hyde_features.py` and the persistence mechanism (`save_project`/`load_project`) should be used as templates for state and `comm` testing.

## Out of Scope

- Implementing interactive graph cursors (this is a future feature, though the architecture must support it).
- Advanced plot editing dialogs (e.g., axis styling dialogs).
- Monkey-patching existing matplotlib backends (explicitly forbidden by specifications).
- Migration shims from older systems.
