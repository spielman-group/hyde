## Problem Statement

The Hyde project is based on the feature set of Igor Pro, and the term "wave" has inadvertently leaked into the codebase, user interface, and specifications. Since Hyde is an independent, modern Pythonic data analysis environment, relying on Igor terminology causes confusion and incorrectly couples Hyde's conceptual model to legacy software. The application should instead use native Python terminology to accurately reflect the underlying data structures being used.

## Solution

Scrub all functional references to "wave" from the codebase, UI labels, default variable names, and active project documentation. Replace "wave" with "array" and "textWave" with "string_array" across the frontend, backend, and documentation, ensuring Hyde uses standard Python nomenclature. References to "wave" will only be preserved in explicit historical comparisons to Igor Pro (e.g., in `IGOR.md` files).

## User Stories

1. As a Hyde user, I want the Python Variables UI filters to say "Arrays" instead of "Waves", so that the terminology aligns with the Python objects (like numpy arrays) I am actually inspecting.
2. As a Hyde user generating new data structures, I want the default variables generated by the application to use Python-native naming conventions (e.g., `array0`, `string_array0`), so that my namespace feels natural and Pythonic.
3. As a developer, I want the internal state dictionaries and IPC communication to use standard python keys (`arrays` instead of `waves`), so that I do not have to translate between legacy Igor terminology and the actual Python data structures being passed around.
4. As a contributor reading the documentation, I want all specifications, architectural documents, and project plans to refer to data structures as "arrays" rather than "waves", so that the architecture accurately describes the system being built.
5. As an archivist of legacy requirements, I want the `IGOR.md` documents to remain completely untouched, so that the historical baseline feature set of Igor Pro remains accurately documented for reference.

## Implementation Decisions

- **Terminology Mapping:**
  - `wave` -> `array`
  - `textWave` -> `string_array`
  - `Waves` -> `Arrays`
- **UI & State Changes (Python Variables & Project State):**
  - The Python Variables checkbox will be renamed from `wavesCheckBox` to `arraysCheckBox`.
  - The internal session state key emitted will be changed from `waves` to `arrays`.
  - **No backwards compatibility will be provided** for older `session.toml` files. Projects with the old `waves` key will simply ignore it and fall back to the default, strictly aligning with the pre-alpha status of the software and the project's architectural mandates.
- **Variable Prefixing (Features Module):**
  - The feature module responsible for generating default variable names will generate `array` and `string_array` prefixes instead of `wave` and `textWave`.
- **Documentation Updates:**
  - All active, present-tense documentation (e.g., `PLAN.md`, `STATUS.md`, and `SPEC.md` files) will be updated to replace "wave" with "array".
  - All `IGOR.md` files will be explicitly excluded from this replacement.

## Testing Decisions

- **Testing Approach:** Tests should verify that the GUI correctly emits the new `arrays` state and that the backend successfully generates `array` and `string_array` variables during actions like Table creation.
- **Modules Tested:**
  - The Python Variables UI filters and serialization logic.
  - The Table features module and its default variable creation.
  - The Project save/load mechanism handling the session state.
- **Prior Art:** Existing tests will be updated directly. The tests will simply have their assertions updated to check for `array0` instead of `wave0`, and `arraysCheckBox` instead of `wavesCheckBox`.

## Out of Scope

- Rewriting or modifying `IGOR.md` or any documents that serve as direct comparisons or historical references to Igor Pro.
- Providing migration tools or backwards compatibility shims for older `session.toml` files containing the old "waves" key.
- Introducing new multi-dimensional array support (this is purely a terminology and refactoring change).
- Modifying pandas DataFrames terminology (DataFrames remain their own distinct structure as agreed upon).

## Further Notes

- This feature is purely a terminology cleanup and refactoring task; no core functionality is being added or removed.
- A script should be carefully applied to ensure all string replacements (such as `wave0` -> `array0` and `textWave` -> `string_array`) are handled safely without breaking unrelated text.
